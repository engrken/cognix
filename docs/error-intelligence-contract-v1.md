# COGNIX Error Intelligence Contract v1

Status: proposed integration contract. This document defines a safe path for SAGA, CLEAR Sys, and ROAMPH to report technical errors to COGNIX. It does not enable ingestion, change application behavior, or authorize automated remediation.

## Objective

When an individual encounters an application error, the owning application may emit a small, authenticated technical event to COGNIX. COGNIX can correlate the event with other failures, compare it with verified incident knowledge, and help operators investigate recurring code or infrastructure problems.

The application remains responsible for displaying the error, protecting the user's work, enforcing authorization, and determining whether an operation succeeded. COGNIX is an advisory incident-intelligence service, not a request proxy and not a source of truth for application transactions.

## Initial delivery model

1. The application detects a server-side error or a specifically allowlisted operational failure.
2. An application-owned adapter converts it into the strict event envelope below.
3. The adapter sends the event server-to-server using that application's dedicated Cognix service credential.
4. COGNIX validates the credential, schema, event age, application identity, and size before accepting it.
5. COGNIX computes its own fingerprint and correlates the event with technical monitoring and verified learning.
6. COGNIX returns an acknowledgement/reference. The application continues to own the user-facing response.
7. An operator reviews unfamiliar patterns and records a cause or resolution only after verification.

Event delivery must be best-effort and asynchronous where practical. A Cognix timeout or outage must not turn a recoverable application request into a second user-facing failure.

## Event envelope

The first version should accept only bounded, allowlisted fields:

| Field | Rule |
|---|---|
| schemaVersion | Exact integer 1 |
| eventId | Random UUID generated by the source application; used only for idempotency |
| occurredAt | ISO-8601 timestamp within a short accepted clock-skew window |
| app | Fixed enum: saga, clear, roamph |
| category | Fixed enum: application_exception, dependency_timeout, database_unavailable, upstream_failure, authentication_failure, authorization_failure, validation_failure, client_render_failure |
| severity | Fixed enum: warning, error, critical |
| component | Short code selected from an app-owned allowlist; never a file path or class name |
| operationCode | Optional short code from an app-owned allowlist; never a raw route, URL, SQL statement, or user action description |
| httpStatus | Optional integer from 400 through 599 |
| dependencyCode | Optional fixed code such as primary_database or payment_provider; no hostname or connection string |
| environment | Fixed enum: production or staging |
| correlationId | Optional random opaque technical ID with no embedded user, tenant, or session information |

COGNIX computes the normalized fingerprint itself. The source application must not choose or override the fingerprint.

## Prohibited data

Never transmit or store:

- Names, email addresses, phone numbers, student/customer/teacher IDs, tenant IDs, account IDs, IP addresses, session IDs, or device fingerprints.
- Passwords, cookies, authorization headers, API keys, tokens, environment variables, or secrets.
- Request or response bodies, form values, uploaded files, database rows, SQL parameters, payment details, academic records, or booking details.
- Raw exception messages, stack traces, source file paths, arbitrary URLs, query strings, or free-form user text.
- Screenshots or browser telemetry that may contain application data.

A correlation ID must be randomly generated and must not be a disguised user or record identifier. If an application needs to investigate which user was affected, it must resolve that correlation locally under its own authorization and audit rules. COGNIX must not be able to reverse-map it.

## Authentication and isolation

- Each application uses its own dedicated server-to-server credential.
- COGNIX derives the application identity from the credential; it must reject a body app value that does not match the authenticated application.
- The legacy shared/compatibility SAGA key must never authorize CLEAR or ROAMPH.
- End-user sessions and browser-supplied credentials are never accepted as service authentication.
- Unknown applications, disabled capabilities, invalid credentials, malformed payloads, stale events, and oversized bodies fail closed.
- The receiver must enforce a small request-size limit, strict schema validation, rate limits per app, and idempotency by (app, eventId).
- COGNIX does not call back into application databases or private application APIs to enrich an event.

## Correlation and response behavior

COGNIX may correlate events using only normalized technical fields such as application, category, component code, operation code, dependency code, HTTP status class, and a coarse time window.

A response may contain:
- Accepted/rejected status.
- An opaque COGNIX event reference.
- A safe classification such as known_pattern, new_pattern, or rate_limited.

It must not return a diagnosis as fact. A known pattern may be described as a candidate match only when the stored resolution was verified and the current evidence is sufficiently similar. Unknown or weak matches are escalated for human review.

COGNIX must not automatically retry user operations, modify application data, change permissions, restart services, edit code, or deploy fixes. The source application owns retries and transaction outcomes.

## Retention and operations

- Keep only the minimum technical event fields needed for correlation and learning.
- Define a bounded retention window and maximum event count before enabling persistent ingestion.
- Avoid high-volume per-request telemetry; emit only actionable failures and aggregate repeated events at the application edge where appropriate.
- Record safe counters for accepted, rejected, deduplicated, and rate-limited events.
- Do not log raw rejected request bodies or secret-bearing headers.
- Ensure event-store writes are bounded, private, concurrency-safe, and fail without affecting the source application.
- Provide an operator-visible explanation of what evidence produced each pattern and how confident the match is.

## Rollout sequence

### Stage A — Contract and threat model
- [x] Define event allowlist and prohibited data.
- [x] Define per-application authentication and identity binding.
- [x] Define best-effort delivery and fail-closed behavior.
- [ ] Review the contract against each source application's error-handling architecture.

### Stage B — Cognix receiver
- [x] Add a dedicated server-to-server endpoint at `/api/v1/errors`.
- [x] Validate app-scoped service authentication and strict schema.
- [x] Add bounded request parsing, event-age validation, per-app rate limiting, idempotency, and private event persistence.
- [x] Add an authenticated operator view at `/admin/errors` without user-identifying information.
- [ ] Validate app adapters and live event delivery before enabling any source application.

### Stage C — Application adapters
- Implement server-side adapters in SAGA, CLEAR Sys, and ROAMPH separately.
- Start with a small allowlist of actionable server-side failures.
- Confirm that event delivery never delays or changes the user transaction outcome.
- Do not enable any app until its credential and data boundary have been reviewed.

### Stage D — Learning and response
- Correlate events with existing monitor snapshots and verified resolutions.
- Show evidence-backed candidate resolutions to operators.
- Record helpful, ineffective, or inconclusive outcomes.
- Introduce user-facing recovery guidance only when the owning application can verify the transaction state.

## Acceptance criteria

- The authenticated application identity cannot be spoofed through the payload.
- No user, tenant, business, academic, financial, or secret data is accepted.
- The endpoint rejects unknown fields and malformed or oversized payloads.
- Repeated event IDs are idempotent.
- Rate limits and storage failures do not affect source application availability.
- Cognix can group similar technical errors without identifying affected users.
- Recommendations distinguish verified fixes from hypotheses.
- No autonomous mutation, code editing, or deployment is performed.
